# edap gRPC 基准 —— 修前 / 修后对比（连接级窗口扩容 + 写路径批量化）

> 目的：量化 §23.2 诊断出的**两个天花板**各自的修复收益。
>
> - **天花板一**：连接级流控窗口恒为 65535 字节，两端都不主动扩大
>   ⇒ 一条连接上最多只有 64KB 在途，并发再高也没用；
> - **天花板二**：写路径是「连接级单锁 + 锁内阻塞 syscall + 每帧一次写」
>   ⇒ 小负载高并发时 62% 的墙钟时间花在锁里的 syscall 上。
>
> 修复：① 两端建连时发 `WINDOW_UPDATE(streamId=0)` 把连接级窗口撑到 1MB，
> 并在 SETTINGS 里通告 `INITIAL_WINDOW_SIZE=1MB`；② 客户端写路径改成
> 「锁内只追加字节、锁外由 leader 线程批量 syscall」的 leader/follower 模型。

## 三、修前 vs 修后（edap 侧）

「修前」列取 README §23.1 公布的修前表；「修后」为 3 批中位数。

| 负载 | 并发 | 修前 req/s | 修后 req/s | 提升 | 修前 edap/google | 修后 edap/google |
|---|---|---|---|---|---|---|
| 0B | 1 | 17,412 | 18,542 | 1.07x | 2.10x | 2.09x |
| 0B | 8 | 31,898 | 63,272 | **1.98x** | 0.98x | **1.97x** |
| 0B | 32 | 31,496 | 77,814 | **2.47x** | 0.87x | **2.19x** |
| 1KB | 1 | 16,713 | 16,752 | 1.00x | 1.82x | 1.76x |
| 1KB | 8 | 29,581 | 62,266 | **2.10x** | 0.96x | **1.98x** |
| 1KB | 32 | 30,310 | 75,288 | **2.48x** | 0.88x | **2.20x** |
| 16KB | 1 | 8,524 | 9,114 | 1.07x | 1.07x | 1.08x |
| 16KB | 8 | 13,353 | 18,582 | **1.39x** | 0.54x | **0.74x** |
| 16KB | 32 | 12,167 | 18,452 | **1.52x** | 0.43x | **0.64x** |
| 64KB | 1 | 3,239 | 4,073 | 1.26x | 0.54x | 0.66x |
| 64KB | 8 | 3,416 | 5,427 | **1.59x** | 0.23x | **0.36x** |
| 64KB | 32 | 3,272 | 5,575 | **1.70x** | 0.22x | **0.37x** |

**读法**：

1. **小负载并发档位是写路径批量化吃下来的**（0B / 1KB @ 8~32 并发 **~2x**）；
   这批场景的连接级窗口从来不是瓶颈（1KB 远小于 64KB 窗口），所以提升**只能**来自写路径。
2. **大负载并发档位是窗口扩容吃下来的**（16KB / 64KB @ 8~32 并发 **1.39x~1.70x**）；
   这批场景的窗口扩容把「一条连接上同时在途的字节」从 64KB 提到 1MB。
3. **单并发几乎没变**（1.00x~1.26x）—— 单并发时没有锁争用、也没有并发在途压力，
   成本主体是编解码与系统调用，与两个天花板都无关。**这与诊断完全吻合**。
4. **相对 grpc-java 的位置**：小负载从「打平」（0.87~0.98x）变成**领先 2x**；
   大负载从 0.22~0.54x 提升到 0.36~0.74x，但**仍然落后**。

## 四、两个天花板各自的贡献（修后中间批次对比）

| 负载 | 并发 | 修前 | 只修窗口（0042） | 窗口 + 批量化（3 批中位数） |
|---|---|---|---|---|
| 0B | 8 | 31,898 | 28,037（0.88x） | 63,272（**1.98x**） |
| 0B | 32 | 31,496 | 30,761（0.98x） | 77,814（**2.47x**） |
| 16KB | 32 | 12,167 | 16,585（**1.36x**） | 18,452（**1.52x**） |
| 64KB | 8 | 3,416 | 4,874（**1.43x**） | 5,427（**1.59x**） |
| 64KB | 32 | 3,272 | 4,716（**1.44x**） | 5,575（**1.70x**） |

**结论**：两个天花板是**互相独立**的，收益不可互相替代：

- **窗口扩容**只对大负载有效（16KB / 64KB），对小负载（0B）**没有任何帮助**
  （28,037 vs 31,898，差异在批间噪声内）；
- **写路径批量化**对小负载是决定性的（~2x），对大负载也有贡献
  （16KB@32 从 1.36x 再到 1.52x；64KB@32 从 1.44x 再到 1.70x）——
  因为大负载每个请求要写很多帧，合并 syscall 同样省。

- **0B / 1KB 档位很稳**（1%~4%）—— 结论可信；

  在途字节接近窗口上限时，**一次慢的 GC / 调度抖动就会把这一档的吞吐打下来**。
  这两档的绝对值不可引用，只看趋势。

## 六、修完还剩什么

**大负载仍然落后 grpc-java**（64KB@32：0.37x）。剩余差距的来源已定位但**未修**：

1. **edap 客户端是「阻塞 socket + 单读线程」**，grpc-java 是 netty NIO ——
   大负载下 edap 的单读线程要自己搬 64KB×并发 的数据，CPU 与拷贝都在关键路径上；
2. **edap 客户端每帧一次写**已经改成批量，但**帧的分片逻辑**（16KB 一帧、按流控窗口切）
   与 grpc-java 的策略不同；
3. grpc-java 的 **HTTP/2 帧压缩（HPACK 动态表）**与 edap 一样，差距不在这里。

⇒ 下一步若要继续追平，方向是「客户端改成 NIO + 多读线程」，属于**架构级改动**，
不是调参能解决的。本轮不做。

**另有一条尾巴没解决**：64KB@32 的 **p99 是 59.8ms**，而 google 是 3.0ms（**20 倍**），
且三个批次都在 55~65ms 区间（不是抖动，是稳定的尾部）。
p50 只有 3.0ms（与 google 同量级）⇒ **不是平均吞吐的问题，是尾部**。
两个候选原因（都未验证）：

- 单读线程一次要搬 32 条流 × 64KB 的数据 ⇒ 某个流一旦排到队尾就等一整轮；
- 客户端 `GrpcClientCall` 的响应缓冲分配 / GC 造成的长尾。

这一条**与吞吐结论独立**，即使吞吐追平了也要单独查。

## 七、复现

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@17
mvn -o -pl edap-grpc-parent/edap-grpc-benchmark -am -DskipTests install
cd edap-grpc-parent/edap-grpc-benchmark
mvn -o -q dependency:build-classpath -Dmdep.outputFile=target/cp.txt -Dmdep.includeScope=runtime
java --add-opens java.base/java.lang=ALL-UNNAMED --add-opens java.base/java.nio=ALL-UNNAMED \
     --add-opens java.base/sun.nio.ch=ALL-UNNAMED --add-opens java.base/java.util=ALL-UNNAMED \
     -cp "target/classes:$(cat target/cp.txt)" io.edap.grpc.benchmark.BenchMain \
     --out target/benchmark-report.md

# 多批次取中位数
python3 scripts/compare-reports.py --out doc/bench/summary-after.md \
        doc/bench/after-batching-20261112-0050.md doc/bench/after-20261112-0105.md \
        doc/bench/after-20261112-0908.md
```

> ★ `exec:java` 跑不了这个基准：它在 Maven 的 JVM 里执行，会踩到
> `java.base does not "opens java.lang"`（edap 的 Unsafe 工具类在类初始化时反射访问
> `String.value`）⇒ 必须用**独立 JVM + `--add-opens`**（与根 pom 的 surefire `argLine` 同一组参数）。
