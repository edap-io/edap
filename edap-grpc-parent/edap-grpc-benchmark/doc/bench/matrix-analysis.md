# edap gRPC —— 2×2 矩阵归因（客户端 × 服务端）

> 目的：把「edap 全栈 vs grpc-java 全栈」这**一个**端到端数字，拆成
> **客户端这一侧**与**服务端这一侧**各自的贡献。
>
> 只测 E→E 与 G→G 两条链路时，客户端与服务端是**同时**换掉的，
> 测出来的差距无法归因 —— 是客户端慢？还是服务端慢？还是两者都慢？

> ★ **本文档已按 2026-11-12 晚「服务端七个瓶颈修完」之后的矩阵重写。**
> 上午那批（`matrix-20261112-{1038,1053,1106}.md`）测的是**没修好的服务端**，
> 数字与结论**全部作废** —— 作废对照表见文末「六、与旧结论的关系」。

---

## 一、实验设计

**2×2 矩阵**（四个臂，每个臂**独占一条连接**）：

| | edap 服务端 | grpc-java 服务端 |
|---|---|---|
| **edap 客户端** | **E→E** | **E→G** |
| **grpc-java 客户端** | **G→E** | **G→G** |

- **换客户端** = `G→E / E→E` —— 服务端不变，**只反映客户端**；
- **换服务端** = `E→G / E→E` —— 客户端不变，**只反映服务端**；
- **全栈** = `G→G / E→E`；
- **交互项** = 全栈 ÷ (换客户端 × 换服务端) —— 接近 1 表示两个维度可加、互不影响。

**调度**：4 臂 × 4 轮，**拉丁方**（第 r 轮第 k 个位置跑第 `(r+k)%4` 个臂）——
每个臂在每个位置各跑一次，位置偏差（JIT 预热、GC、机器负载漂移）被均摊掉。

**测量口径**：预热 1000ms + 测量窗口 3000ms（时间制）；N 个 worker 线程共享一条连接；
两侧服务端跑在**同一个 JVM**，业务逻辑逐行对齐（name 加前缀、value ×2、blob 原样回显）。

> ★ **流控窗口两边对齐到 8MB**（`-Dedap.grpc.connWindow` / `-Dbench.google.connWindow`）——
> 之前 edap 侧 8MB、grpc-java 侧 1MB，差 8 倍 ⇒ 同一场景不是同一口径。
> 这个对齐本身就是一轮修正：**它把「客户端给了多少额度」这个变量从矩阵里消掉了**。

**前置自检**：跑基准**之前**先做双向互操作自检（edap 客户端 → google 服务端、
google 客户端 → edap 服务端），不通就直接失败退出 —— 否则测出来的数字没有意义。

**批次**：2026-11-12 晚三批（`matrix-20261112-fix-{1,2,3}.md`），下表取**三批中位数**。
配对脚本 `scripts/compare-reports.py`；纯数据表 [`matrix-summary.md`](.)。

> ⚠ 机器是开发机（10 核，loadavg 常 10~25）⇒ **绝对值不可跨批次比较**，
> 结论只看「同一批次内的相对关系」与「跨批次的中位数」。

## 三、结论

### ③.1 edap 服务端比 grpc-java 服务端**更快**（全档位）

**用户问题的直接答案**：把服务端换成 grpc-java，**每一档都变慢**。

| 64KB @ 32 并发 | req/s | 相对 E→E |
|---|---|---|
| **E→E（edap 客户端 + edap 服务端）** | **19,207** | **1.00x（基准）** |
| **G→E（换成 grpc-java 客户端，服务端不动）** | **19,803** | **1.04x** |
| **E→G（客户端不动，换成 grpc-java 服务端）** | **15,080** | **0.79x** |
| G→G（两边都换） | 15,594 | 0.81x |

「换服务端」= **0.51x ~ 0.85x**（全 12 档）⇒

| 负载 @ 32 并发 | edap 服务端 | grpc-java 服务端 | edap 快多少 |
|---|---|---|---|
| 0B | 77,016 | 39,432 | **1.95x** |
| 1KB | 75,656 | 38,963 | **1.94x** |
| 16KB | 45,048 | 29,428 | **1.53x** |
| 64KB | 19,207 | 15,080 | **1.27x** |

⇒ **大负载的差距不是「edap 慢」，而是「edap 快」**；
⇒ 交互项 0.95x ~ 1.15x ≈ 1 ⇒ 两个维度可加、无耦合。

### ③.2 小负载的 2x 领先也是**服务端**给的

0B @ 32 并发：**换客户端** 0.99x（几乎无变化）；**换服务端** 0.51x
⇒ edap 服务端比 grpc-java 服务端**快 1.95 倍**。

### ③.3 客户端侧已经拉平（不再是短板）

「换客户端」= `G→E / E→E` = **0.84x ~ 1.09x**，全表噪声级：
大负载上 grpc-java 客户端快 4~9%，小负载上 edap 客户端快 6~19%，**互有胜负**。

（上午那批里「1KB@32 换客户端 +21%」的反例消失了 —— 它也是服务端的锅。）

### ③.4 「350MB/s 带宽墙」不存在了

把吞吐换算成字节率（req/s × 线上字节数）：

| 负载 @ 32 | edap 服务端 | grpc-java 服务端 |
|---|---|---|
| 16KB | **744 MB/s** | 476 MB/s |
| 64KB | **1,204 MB/s** | 981 MB/s |

edap 服务端的字节率现在**随负载增大**（744 → 1,204 MB/s），
不再是上午那批的平线（310 / 369 MB/s）。
⇒ 上午推导的「固定字节率上限」是**服务端瓶颈的副产品**，不是独立的架构限制。

### ③.5 60ms 长尾消失了

64KB @ 32 并发的 p99：

| 臂 | p99（现在） | p99（上午那批） |
|---|---|---|
| E→E | **2,852μs** | 60,614μs |
| E→G | 4,031μs | 3,164μs |
| G→E | 3,056μs | 7,964μs |
| G→G | 2,926μs | 2,812μs |

> 口径：每臂 4 轮的 p99 先取中位数得到「该批次的臂 p99」，再对三批取中位数。
> （`compare-reports.py` 只解析 req/s，p99 是按报告里「四、原始轮次」表另算的。）

⇒ 全部落在 2.9~4.0ms 量级。**长尾是服务端造成的**（不是客户端的独立缺陷）。
剩下相对最差的一格是 E→G 的 4.0ms —— 那是 **edap 客户端**读大响应的尾巴，与服务端无关。

## 四、服务端这边到底修了什么

七个瓶颈的完整记录见 README §23.6。这里只列**归因链**：

| # | 瓶颈 | 性质 | 64KB@32 的影响 |
|---|---|---|---|
| 一 | socket 发送缓冲被钉死 16KB | 参数 | 5,451 → 11,077 req/s |
| 二 | 写缓冲只有 32KB | 参数 | 一条 64KB 响应拆成 4 次 socket 写 |
| 三 | 读缓冲只有 16KB（装不下 HTTP/2 最大帧） | 参数 | 10,653 → 14,903 req/s |
| 四 | 连接级流控窗口只撑到 1MB | 参数 | 15,076 → 18,966 req/s，p99 15.2ms → 2.7ms |
| 五 | 出站每帧 `new byte[]` + 整块拷贝 | 数据结构 | 少一次整块拷贝 + 少一批分配 |
| 六 | `streams` 用 `HashMap` | 正确性 | 并发一高就全部超时（CME） |
| **七** | **出站缓冲「换缓冲」是平方级拷贝** | **逻辑** | **6,418 → 15,162 req/s（+136%）** |

★ **根因七只在「连接复用 + 大响应」下暴露**：
缓冲每轮 flush 都被丢弃重来（`releaseBuffer(buf); buffer = null;`），
于是每轮都要重演一遍「缓冲一帧一帧地长、每次都把已累积的整块搬走」，
5 秒搬了 **26GB** 而实际输出只有 **1.9GB** ⇒ **15 倍拷贝放大**。
**一连接一请求的基准永远发现不了它** —— 矩阵基准每臂跑 4 轮 × 3 秒，
连接复用的累积效应被算进了平均值 ⇒ **上午那批矩阵数字被系统性拉低**。

## 五、已排除的方向（别再往这边钻）

| 假设 | 实测 | 判定 |
|---|---|---|
| GC / 分配是瓶颈 | `-Xmn2g` 对比默认：42,035 vs 42,008 req/s（无差异） | ❌ |
| CPU 是瓶颈 | 16KB 负载下整个进程只用 3.4 / 10 核 | ❌ |
| 编解码器是瓶颈 | 16KB / 64KB 的解码两边基本持平 | ❌ |
| 诊断计数器有开销 | `-Dedap.http2.writeStats` 开 / 关：19,015 vs 18,323、19,006 vs 19,677（±4% 噪声） | ❌ |
| 客户端架构（阻塞 socket + 单读线程）是短板 | 换客户端 = 0.84x ~ 1.09x | ❌ |

⇒ **JFR 在本机基本失效**（`jdk.ExecutionSample` 只有 17 个样本）——
这些结论全部来自**逐段插桩 + 参数扫描 + 对照实验**。

## 六、与旧结论的关系（**上午那批的数字与结论被本轮取代**）

| 上午的结论 | 本轮数据 | 判定 |
|---|---|---|
| 「大负载落后 grpc-java 是**客户端**的架构问题（阻塞 socket + 单读线程），下一步把客户端改成 NIO + 多读线程」 | 换客户端 1.04x；瓶颈在服务端 | ❌ **归因错误，作废**（方向对：确实在服务端） |
| 「64KB@32 换服务端 = 2.68x ⇒ edap 服务端比 grpc-java 慢」 | 换服务端 0.79x ⇒ **edap 服务端快 1.27x** | ❌ **数字与结论作废** |
| 「edap 服务端撞到 350MB/s 带宽墙」 | 744 → 1,204 MB/s，**没有墙** | ❌ 作废 |
| 「64KB@32 的 p99 = 60ms 是交互出来的」 | p99 = 2.8ms，**长尾本身没了** | ❌ 作废（问题不存在了） |
| 「1KB@32 换客户端 +21% ⇒ edap 客户端是短板」 | 换客户端 0.97x | ❌ 作废 |
| 「下一步方向改成『查 edap 服务端的写路径』」 | 已查完，定位到七个瓶颈并全部修复 | ✅ **已完成** |

★ **为什么上午那批会错**：它测的是**没修好的服务端**，
而根因七（平方级拷贝）**只在连接复用时暴露** ——
矩阵每臂跑 4 轮、每轮 3 秒，复用连接的累积效应被算进了平均值 ⇒ 数字被系统性拉低。
**教训：矩阵基准的「一臂多轮」设计，正好放大了「随时间退化」的 bug。**

## 七、复现

```bash
export JAVA_HOME=/opt/homebrew/opt/openjdk@17
cd /Volumes/Data/NetBeansProjects/edap/edap-grpc-parent/edap-grpc-benchmark
mvn -o -q dependency:build-classpath -Dmdep.outputFile=target/cp.txt -Dmdep.includeScope=runtime

# 一批矩阵（两边流控窗口对齐到 8MB）
java --add-opens java.base/java.lang=ALL-UNNAMED --add-opens java.base/java.nio=ALL-UNNAMED \
     --add-opens java.base/sun.nio.ch=ALL-UNNAMED --add-opens java.base/java.util=ALL-UNNAMED \
     -Dbench.google.connWindow=8388608 \
     -cp "target/classes:$(cat target/cp.txt)" io.edap.grpc.benchmark.BenchMain \
     --blob 0,1024,16384,65536 --conc 1,8,32 --rounds 4 --warmup 1000 --measure 3000 \
     --out doc/bench/matrix-20261112-fix-1.md

# 多批次取中位数（端到端 + 2×2 矩阵）
python3 scripts/compare-reports.py --out doc/bench/matrix-summary.md \
        doc/bench/matrix-20261112-fix-1.md doc/bench/matrix-20261112-fix-2.md \
        doc/bench/matrix-20261112-fix-3.md

# 换客户端探针（同一服务端，换客户端；带服务端侧计数）
java ... -Dedap.http2.writeStats=true -Dedap.grpc.connWindow=8388608 \
     -Dbench.google.connWindow=8388608 \
     -cp "target/classes:$(cat target/cp.txt)" io.edap.grpc.benchmark.CrossClientProbe \
     --blob 16384,65536 --conc 32 --measure 5000 [--fresh-client] [--server google]
```

> ★ **不能用 `exec:java`**：它在 Maven 的 JVM 里执行，会踩到
> `java.base does not "opens java.lang"`（edap 的 Unsafe 工具类在类初始化时反射访问
> `String.value`）⇒ 必须用**独立 JVM + `--add-opens`**（与根 pom 的 surefire `argLine` 同一组参数）。
>
> ★ **跑基准期间不要 `mvn install`**：基准的 classpath 指向 `~/.m2` 里的 jar，
> 装新 jar 会让同一批实验的前后两半用了不同的代码。`mvn compile` 是安全的。
